# V2 Work Item Foundation

## Purpose

A Work Item is an authorized unit of operational work created to move a situation toward a verifiable outcome.

It is not an observation, event, diagnosis, action, verification, or situation resolution.

## Domain position

Observation → Event → Situation → Work Item → Action / Execution → Verification → New Evidence

A Situation answers: what currently requires attention?

A Work Item answers: what operational response has been organized, who is accountable, and by when?

One situation may produce multiple work items. Completing a work item never automatically resolves its situation.

## Current schema

work_items is tenant-scoped and includes:

- organization_id
- situation_id
- work_type
- status
- priority
- title / description
- customer/site/asset subject references
- assigned_actor_id
- assigned_at / due_at / completed_at
- created_by_actor_id
- correlation_id
- optional idempotency_key
- timestamps

Initial work types:

- INVESTIGATE
- CONTACT_CUSTOMER
- VISIT_SITE
- RECONCILE_PAYMENT
- ESCALATE_EXTERNAL

Initial statuses:

- OPEN
- ASSIGNED
- IN_PROGRESS
- COMPLETED
- CANCELLED

Initial priorities:

- LOW
- NORMAL
- HIGH
- URGENT

## Integrity and authorization

The database enforces:

1. Work Item and Situation share the same organization through a composite tenant-scoped foreign key.
2. Optional customer/site/asset subjects must belong to the same organization.
3. Creation requires work.execute.
4. Assignment requires work.assign.
5. Status transitions require work.execute.
6. Assignees must be ACTIVE actors with ACTIVE memberships in the same organization.
7. The creator is taken from the authenticated actor context rather than trusted from the client payload.
8. Terminal states (COMPLETED, CANCELLED) are immutable.
9. Invalid lifecycle transitions are rejected.
10. (organization_id, idempotency_key) is unique when an idempotency key is supplied.
11. Work completion does not mutate Situation status.

## Lifecycle

Allowed transitions:

OPEN → ASSIGNED / CANCELLED

ASSIGNED → IN_PROGRESS / OPEN / CANCELLED

IN_PROGRESS → COMPLETED / ASSIGNED / CANCELLED

Assignment of an active actor to OPEN work moves it to ASSIGNED. Unassignment from ASSIGNED work returns it to OPEN. IN_PROGRESS work cannot be left without an assignee.

## History

work_item_history is append-only from the application role.

It records:

- creation
- assignment / unassignment
- start
- completion
- cancellation

Authenticated clients have SELECT only. History rows are generated by a protected database trigger attached to real work-item changes, so a client cannot manufacture a parallel history.

## Security boundary

Both tables have RLS enabled and forced.

Work-item reads require work.read.

Work-item writes are constrained by RLS plus trigger-owned authorization checks for execution and assignment.

No DELETE policy or authenticated DELETE grant exists. Work is cancelled rather than deleted.

Tenant consistency is enforced by direct organization_id plus composite foreign keys and active-membership checks.

## Idempotency

The optional idempotency key is scoped to the organization:

UNIQUE (organization_id, idempotency_key) when the key is non-null.

This prevents duplicate work creation when a future channel or external integration retries the same request.

## Explicit non-goals

This gate does not introduce:

- Action / execution records
- Verification
- Ellie
- console/UI
- WhatsApp or Telegram adapters
- telemetry
- inventory
- scheduling
- route optimization
- teams or skills
- maintenance module
- marketplace / PCU / wallet / cluster / settlement domains
- generic workflow/no-code engine

The next architectural gate is Action / Execution, followed by a separate Verification gate.
