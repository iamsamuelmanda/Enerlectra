# Enerlectra Core — Intelligence & Capability Convergence Contract

**Status:** Active architectural decision for PR #35  
**Date:** 2026-10-06  
**Branch:** `reconstruction/platform-identity-boundary`

## 1. Decision

`enerlectra-core` is **not** a disposable legacy package.

It contains two materially different classes of software:

1. reusable Enerlectra platform/intelligence/integration infrastructure; and
2. legacy economic/protocol domain systems whose tenant and product boundaries do not match the V2 operational kernel.

The correct convergence strategy is therefore:

> **Preserve the soul. Replace the boundary. Isolate the old product model.**

No blanket deletion, package removal, or global rewrite of `enerlectra-core` is authorized by this document.

---

This is accumulated product/IP, not merely dead code.

The fact that some of these modules currently depend on unsafe or obsolete tenant assumptions does **not** mean the underlying capability is obsolete.

## 3. The new boundary

The canonical architecture is:

```
Actor
  ↓
Membership
  ↓
Organization
  ↓
Operating Context
  ↓
Capabilities + Policies + Responsibility Scope
  ↓
Operational Resources
  ↓
Observation / Evidence
  ↓
Event
  ↓
Situation
  ↓
Recommendation
  ↓
Work
  ↓
Action
  ↓
Verification
  ↓
Audit
```

Ellie operates over this context:

```
Authorized Actor Context
        +
Organization Context
        +
Operating Model
        +
Capabilities
        +
Policies
        +
Authorized Evidence
        ↓
      Ellie
        ↓
Recommendation / Structured Intent
        ↓
Canonical Action + Authorization Boundary
```

Ellie is intelligence, not authority.

AI output never becomes authorization merely because it was generated by Ellie.

## 4. Ellie is a first-class architectural concern

The existing core already contains an embryonic intelligence pipeline:

```
Incoming message
  ↓
Intent resolution
  ↓
Command creation
  ↓
Command bus
  ↓
Intelligence service
  ↓
Ellie worker
  ↓
Context builder
  ↓
LLM inference
  ↓
Outgoing channel response
```

This is valuable and should be preserved conceptually.

However, the current context builder is not yet a V2-safe implementation.

The current implementation retrieves legacy concepts such as:

- customer;
- transactions;
- alerts;

using direct database queries and identifier matching.

It does **not yet enforce the complete V2 context contract**:

```
Actor
→ active Membership
→ Organization
→ permissions
→ operating context
→ capabilities
→ policies
→ authorized operational evidence
```

Therefore:

> **The Ellie pipeline is KEEP/ADAPT, not RETIRE.**

## 5. Ellie migration target

The existing `EllieWorker` should eventually consume a bounded V2 intelligence context rather than directly constructing arbitrary legacy database context.

Target abstraction:

```ts
interface EllieContext {
  actorId: string;
  organizationId: string;
  permissions: string[];
  operatingContext: unknown;
  capabilities: unknown;
  policies: unknown;
  situations: unknown[];
  recommendations: unknown[];
  work: unknown[];
  evidence: unknown[];
}
```

The exact TypeScript shape is intentionally deferred until the V2 intelligence API is implemented.

The important invariant is:

> Ellie receives already-authorized context. Ellie does not decide what tenant data it is allowed to retrieve.

These contain reusable architectural value:

These modules must lose assumptions about:

- `telegram_users.organization_id` as canonical authority;

- unrestricted tenant queries.

### ADAPT as operational capabilities

These may become part of the canonical operational platform when an actual workflow requires them:

- meter observations;

- production verification;
- customer/payment evidence;
- payment exception handling;
- Lenco/mobile-money adapters;

The migration pattern is:

```
legacy capability
  ↓

  ↓
canonical Actor/Organization context
  ↓
V2 resource/evidence model
  ↓
bounded operational workflow
```

Do not copy the old database model merely to reuse the algorithm.

---

### ISOLATE from the V2 operational kernel

Isolation means these systems remain available for historical/reference/future bounded capabilities where appropriate.

It does **not** mean deleting their implementation before their actual production dependencies are understood.

## 7. Particularly important: financial capability is not discarded

The payment and treasury code contains potentially reusable financial infrastructure.

However, payment evidence and operational payment exceptions are not the same thing as a universal financial accounting system.

V2 first needs:

```
payment evidence
→ operational interpretation
→ situation
→ recommendation
→ authorized work/action
→ verification
```

A full settlement/treasury capability can later be attached as a bounded context.

This preserves the underlying engineering without allowing the old financial architecture to define Enerlectra's tenant model.

## 8. Current critical defect in the old intelligence path

The existing `context-builder.ts` uses a Supabase client to query:

- `customers`
- `transactions`
- `alerts`

and resolves a target through phone/meter identifiers.

That is useful historical behavior, but it is **not yet sufficient for V2**.

The correct future sequence is:

```
Channel identity
  ↓
Actor
  ↓
active Membership
  ↓
Organization
  ↓
permission/context resolution
  ↓
authorized operational retrieval
  ↓
Ellie context
  ↓
inference
```

A phone number or meter number may identify a subject.

It must never identify the tenant by itself.

---

## 9. Existing execution context is a strong bridge

The existing `ExecutionContext` already carries:

- `actorId`;
- `organizationId`;
- `correlationId`;
- injected Supabase client;
- logger;
- telemetry;
- optional AI context.

This is close to the V2 architectural direction.

The important change is not to throw it away.

The important change is to make the context **canonical and authoritative**:

```
ExecutionContext
  =
trusted Actor
+
trusted Organization
+
permissions
+
operating context
+
correlation metadata
+
authorized data-access boundary
```

The current interface should therefore evolve rather than be discarded.

---

## 10. Legacy identity code must not become the V2 authority

The existing core contains identity helpers that still know about:

- `telegram_users`;
- legacy `users`;
- cluster selection;
- legacy roles;
- legacy organization fields.

These are legacy adapters.

They cannot be the canonical V2 authorization mechanism.

The V2 authority remains:

```
auth identity
→ Actor
→ active Membership
→ Role
→ Permission
→ Organization
```

Where a channel needs compatibility, an adapter may translate:

```
WhatsApp / Telegram identity
→ Channel Identity
→ Actor
→ Membership
```

The adapter must not create authority by itself.

---

## 11. One implementation per capability

A major convergence risk is accidentally maintaining:

- old meter validation + new meter validation;
- old payment orchestration + new payment orchestration;
- old Ellie + another unrelated AI assistant;
- old workflow engine + a second competing workflow engine.

The goal is not two implementations.

The goal is:

> **one canonical capability implementation behind one canonical boundary.**

During migration, an old implementation may remain temporarily isolated. Once the adapted implementation is proven, the obsolete path can be retired.

---

## 12. What this means for PR #35

PR #35 should therefore be understood as establishing the **authority and operational kernel**, not as completing the entire Enerlectra product.

The merge does not mean:

> `enerlectra-core` is finished or obsolete.

It means:

> V2 now provides the canonical boundary that future capabilities can safely converge into.

Post-merge work should prioritize the highest-value capabilities based on actual ICP/pilot evidence.

The next technical intelligence slice should be:

1. Define a V2 `EllieContext` contract.
2. Define a server-side intelligence data-access boundary.
3. Resolve Actor → Membership → Organization before retrieval.
4. Retrieve only organization-authorized operational evidence.
5. Preserve existing Ellie inference behavior initially.
6. Produce structured recommendation output.
7. Persist important recommendations through the canonical V2 recommendation model.
8. Keep authorization outside Ellie.

10. Reconnect WhatsApp only through the canonical channel-identity path.

Only after this is proven should legacy Ellie context queries be retired.

## 14. Final architectural decision

Enerlectra's accumulated core is part of the product's history and IP.

The convergence target is therefore not:

```
V1 core → delete
V2 → replace it
```

It is:

```
Enerlectra Core
       │
       ├── Platform / workflow / integration infrastructure
       │          ↓
       │       KEEP / ADAPT
       │
       ├── Ellie / intelligence
       │          ↓
       │       ADAPT into V2 context boundary
       │
       ├── Operational capabilities
       │          ↓
       │       ADAPT when ICP validates them
       │
       └── Economic / protocol domains
                  ↓
              ISOLATE
                  ↓
       future bounded capabilities or retirement
```

**The soul stays. The authority boundary changes.**

This is the governing rule for subsequent Enerlectra convergence work.


## 2026-10-07 canonical Ellie context seam

The convergence work now includes a non-breaking intelligence boundary in `enerlectra-core`:

- `EllieContext` is a typed contract containing actor, organization, permissions, operating context, capabilities, policies, evidence, situations, recommendations and work.
- `ExecutionContext.ellieContext` is optional so existing channel runtimes remain functional during migration.
- `EllieWorker` prefers the canonical context when supplied and falls back to the existing context-builder only for legacy callers.
- The legacy context-builder is therefore explicitly an adapter path, not the future tenant authority.

No V2 caller is wired to this seam yet. That is deliberate: the next step is to construct the context from the already-validated V2 tenant resolver and operational queue, rather than allowing Ellie to query legacy customer/transaction/alert tables directly.


## 2026-10-07 canonical Ellie context construction

The next boundary has now been implemented on the server side in:

`server/src/platform/intelligence/ellie-context-builder.ts`

The builder is intentionally not a second database context model. It accepts two already-authoritative inputs:

1. `TenantContext` from the V2 tenant resolver.
2. The canonical operational queue assembled by the V2 operations route.

It produces the existing `EllieContext` contract without granting Ellie any authorization authority.

The construction is:

```
trusted bearer
  ↓
TenantContextResolver
  ↓
Actor + Organization + Membership
  ↓
Role + Permissions
  ↓
Operating Context + Capabilities + Policies
  ↓
canonical operational queue
  ↓
situations + work + recommendations
  ↓
action attempts as operational evidence
  ↓
EllieContext
  ↓
EllieWorker / inference
```

Important boundary properties:

- permissions are copied from the trusted tenant resolver, not from the browser or message;
- organization identity comes from the resolved membership;
- capabilities and policies come from the organization operating context;
- situations, work and recommendations are already organization-scoped by the canonical operations query;
- completed action attempts can be represented as evidence for reasoning;
- Ellie receives context for reasoning but does not receive permission to authorize or execute actions;
- the legacy `captureMessageContext` path remains available only as a compatibility adapter.

A focused test was added at:

`test/v2-ellie-context-builder.test.mjs`

It verifies that the resulting context retains the trusted actor/organization/permission boundary and maps operational work, recommendations and attempt evidence into the canonical intelligence contract.

This is a construction seam, not a production channel cutover. WhatsApp remains fail-closed until its channel identity path is explicitly connected to the V2 tenant boundary.
